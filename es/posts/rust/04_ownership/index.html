Rust - Básico - 04 - Propiedad

2022-01-03 Rust

Propiedad

Comprensión

En los datos del heap, let b = a; solo hace una copia superficial y además a queda invalid, sin acceso (es decir, se produce un move)

Para que sea una copia profunda hay que escribir let b = a.clone();; en ese caso a sigue siendo accesible

Si el tipo del parámetro de entrada de una función se declara como String, se produce una copia superficial (el valor entrante se mueve), mientras que si se usa una reference (&String) no se mueve

(el proceso de crear una reference se llama borrowing)

Si queremos modificar el valor a través de la reference, el parámetro de entrada debe declararse como &mut String

En un mismo momento, sobre los mismos datos de origen

solo puede haber una reference &mut declarada (mutable), o

pueden haber varias references & declaradas (inmutables).

No permitido: dentro del scope de una reference, que existan a la vez let &b = a y let mut &c = a, es decir, no se puede hacer borrow de una reference inmutable y de una mutable al mismo tiempo

El compilador garantiza que las references son valid en tiempo de compilación, así que no existen las Dangling References

Rust tiene esta annotation llamada trait; por ahora no sabemos qué es

Fuente

https://doc.rust-lang.org/book/ch04-00-understanding-ownership.html

…

Rust tiene una anotación especial llamada trait Copy que podemos poner en tipos como los enteros que se almacenan en la pila (hablaremos más de los traits en el capítulo 10). Si un tipo implementa el trait Copy, una variable antigua sigue siendo utilizable después de la asignación. Rust no nos dejará anotar un tipo con el trait Copy si el tipo, o alguna de sus partes, ha implementado el trait Drop. Si el tipo necesita que ocurra algo especial cuando el valor sale del alcance y añadimos la anotación Copy a ese tipo, obtendremos un error en tiempo de compilación. Para aprender a añadir la anotación Copy a tu tipo para implementar el trait, consulta «Derivable Traits» en el apéndice C.

Entonces, ¿qué tipos implementan el trait Copy? Puedes consultar la documentación del tipo en cuestión para asegurarte, pero como regla general, cualquier grupo de valores escalares simples puede implementar Copy, y nada que requiera asignación de memoria ni que sea alguna forma de recurso puede implementar Copy. Estos son algunos de los tipos que implementan Copy:

  • Todos los tipos enteros, como u32.
  • El tipo booleano bool, con los valores true y false.
  • Todos los tipos de coma flotante, como f64.
  • El tipo carácter char.
  • Las tuplas, si solo contienen tipos que también implementan Copy. Por ejemplo, (i32, i32) implementa Copy, pero (i32, String) no.

Nombre de archivo: src/main.rs


    let mut s = String::from("hello");

    let r1 = &mut s;
    let r2 = &mut s;

    println!("{}, {}", r1, r2);

Aquí está el error:


$ cargo run
   Compiling ownership v0.1.0 (file:///projects/ownership)

  |
4 |     let r1 = &mut s;

5 |     let r2 = &mut s;
  |              ^^^^^^ second mutable borrow occurs here
6 |
7 |     println!("{}, {}", r1, r2);
  |                        -- first borrow later used here

error: could not compile `ownership` due to previous error

Este error dice que este código no es válido porque no podemos tomar prestado s como mutable más de una vez a la vez. El primer préstamo mutable está en r1 y debe durar hasta que se use en el println!, pero entre la creación de esa referencia mutable y su uso intentamos crear otra referencia mutable en r2 que toma prestados los mismos datos que r1.

…

Como siempre, podemos usar llaves para crear un alcance nuevo, lo que permite varias referencias mutables, solo que no simultáneas:


    let mut s = String::from("hello");

    {
        let r1 = &mut s;
    } // r1 sale del alcance aquí, así que podemos crear una referencia nueva sin problemas.

    let r2 = &mut s;

Existe una regla parecida para combinar referencias mutables e inmutables. Este código da un error:


    let mut s = String::from("hello");

    let r1 = &s; // sin problemas
    let r2 = &s; // sin problemas
    let r3 = &mut s; // GRAN PROBLEMA

    println!("{}, {}, and {}", r1, r2, r3);

Aquí está el error:


$ cargo run
   Compiling ownership v0.1.0 (file:///projects/ownership)
error[E0502]: cannot borrow `s` as mutable because it is also borrowed as immutable
 --> src/main.rs:6:14
  |
4 |     let r1 = &s; // no problem
  |              -- immutable borrow occurs here
5 |     let r2 = &s; // no problem
6 |     let r3 = &mut s; // BIG PROBLEM
  |              ^^^^^^ mutable borrow occurs here
7 |
8 |     println!("{}, {}, and {}", r1, r2, r3);
  |                                -- immutable borrow later used here

For more information about this error, try `rustc --explain E0502`.
error: could not compile `ownership` due to previous error

¡Uf! Tampoco podemos tener una referencia mutable mientras tenemos una inmutable. ¡Quien usa una referencia inmutable no espera que los valores cambien de repente bajo sus pies! Sin embargo, varias referencias inmutables sí están bien, porque quien solo está leyendo los datos no tiene forma de afectar a la lectura que hacen los demás.

Fíjate en que el alcance de una referencia empieza donde se introduce y continúa hasta la última vez que se usa esa referencia. Por ejemplo, este código compilará porque el último uso de las referencias inmutables, el println!, ocurre antes de que se introduzca la referencia mutable:


    let mut s = String::from("hello");

    let r1 = &s; // sin problemas
    let r2 = &s; // sin problemas
    println!("{} and {}", r1, r2);
    // las variables r1 y r2 no se usarán después de este punto

    let r3 = &mut s; // sin problemas
    println!("{}", r3);

Las reglas de las referencias

Recapitulemos lo que hemos hablado de las referencias:

  • En cualquier momento puedes tener o bien una referencia mutable o bien cualquier número de referencias inmutables.
  • Las referencias siempre deben ser válidas.
